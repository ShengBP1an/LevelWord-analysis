# BreakLD 文档交付协议

## 适用范围

用户要求 Word、DOCX、报告整合、一键复制、迁移到其他文档、打印版或 PDF 时读取本协议。内容研究仍以 BreakLD 主流程和对应参考文件为准；本协议只负责“什么时候开始生成”和“如何交付可编辑文档”。

## 强制确认门

在内容稿、来源和图例计划准备好后，先向用户汇报拟生成配置，再提问并等待明确答复。不得把用户早先提出的文档需求当作最终生成确认。

至少展示以下配置：

- 文件类型：默认仅 `.docx`；PDF 只在用户要求时附加。
- 内容范围：完整版、精简版或用户指定章节。
- 标题与文件名：给出拟用值。
- 署名和日期：未指定时写“无署名、使用当前日期”，不要擅自添加机构。
- 图例：列出原图、标注图、抽象图、方案图的数量与处理方式。
- 版式：默认“紧凑型分析报告，可编辑，可整篇复制”。

推荐确认话术：

> 分析内容、来源和图例已经准备好。拟生成：`[文件类型]`；范围：`[内容范围]`；标题/文件名：`[名称]`；图例：`[处理方式]`；版式：紧凑型可编辑报告。是否按以上配置开始生成？如需调整，请直接指出。

必须遵守：

1. 用户明确回复“是、确认、开始生成”或同等意思后，才能开始文档 authoring。
2. 用户提出修改时，先更新配置，再次询问是否生成。
3. 用户没有回复时暂停；不得创建空白占位文档，不得运行生成命令。
4. 如果用户只要求先看模板，先展示模板，不生成文件。

## 生成工作流

取得确认后：

1. 调用可用的文档制作 skill，并完整遵守其创建、样式、渲染和交付规则。
2. 加载工作区规定的 Python、Node 和文档依赖；不要使用不受控的系统运行时。
3. 在第一次写入命令前，按文档 skill 要求运行一次且仅一次 authoring marker。
4. 在可写工作区构建文档，不直接在 skill 目录或依赖目录生成临时文件。
5. 默认采用适合密集案例研究的紧凑参考指南版式；如用户提供 Word 模板，以用户模板为设计权威。
6. 只在用户明确要求时同时生成 PDF；内部 QA 的 PDF 与页面 PNG 不作为交付物。

## 可复制性要求

目标是让用户能在 Word 中使用 `Ctrl+A → Ctrl+C → Ctrl+V` 一次迁移全部内容。

- 使用真实 Word 标题样式建立层级，不用加粗正文冒充标题。
- 使用真实编号和项目符号，不把序号、圆点或换行列表写成普通文本。
- 对真正的行列数据使用真实表格，设置固定列宽、单元格边距和跨页重复表头；普通解释性文字不要塞进大表格。
- 图片采用行内嵌入，不使用容易漂移的浮动对象；题注紧邻图片。
- 超链接必须可点击；来源名称、作者或机构、日期和 URL 保持可读。
- 关键结论不能只存在于图片里；示意图里的核心关系还要在正文说明。
- 不使用只有本机才存在的字体、外链图片或无法打包的临时资源。

## BreakLD 文档结构

默认顺序：

1. 标题、游戏、地图、模式、研究日期和版本边界。
2. 核心结论摘要与证据等级说明。
3. breakld-template.md 的完整标题骨架。
4. 图例与题注，按首次引用位置嵌入。
5. 问题、改进方案、验证指标和通过标准。
6. 适用边界、未知项和来源清单。

如果篇幅较长，可加自动目录；不要为了目录牺牲复制稳定性。

## 图像嵌入规则

- 原图：保持原始内容；允许等比缩放和必要裁边，但记录裁切，不改色、不补画、不移动结构。
- 标注图：从原图副本生成，保留未标注基准图；标注层只添加必要箭头、区域、编号和图例。
- 抽象图：明确写“分析示意图，不是官方平面图”，不伪装成精确比例地图。
- 方案图：明确写“方案设想，尚未实装”，与未修改基准并列。
- AI 生成图不得充当案例事实证据。
- 每张图提供编号、身份、来源、用途和证据边界；不同版本或模式不得混作同一张事实图。

## QA 与交付门槛

交付前必须：

1. 渲染 DOCX 为逐页 PNG，并以 100% 缩放检查每一页。
2. 检查标题层级、正文、编号、表格、图片、题注、页眉页脚和超链接。
3. 修复文字裁切、对象重叠、图片变形、断表、表头缺失、乱码、题注脱离和异常大空白。
4. 运行图片与可访问性审计；确认图片为嵌入式、表格表头正确、无高等级问题。
5. 用 Word 或兼容程序实际打开一次；如渲染失败，只能按文档 skill 的回退规则交付并明确披露。
6. 默认只返回最终 `.docx`；不附构建脚本、页面 PNG、内部 PDF 或中间稿，除非用户要求。

推荐文件名：`BreakLD-<游戏>-<地图>-分析报告.docx`。若文件名冲突，保留旧文件并增加日期或版本号，不静默覆盖。
